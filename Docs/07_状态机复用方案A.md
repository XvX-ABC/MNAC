# 状态机复用方案 A：Definition + Factory

## 1. 背景

当前状态机的组装方式是「先 new 状态，再 AddState，再 AddTransition」：

```csharp
var machine = new PlayableStateMachine<Context>("Enemy");
var idle = new IdleState();
var chase = new ChaseState();
machine.AddState(idle);
machine.AddState(chase);
machine.SetInitialState(idle);
machine.AddTransition(idle, chase, 0.2f, () => context.Distance < 5f);
```

这套 API 本身没问题，问题在于**图结构和实例混在一起**：

- 同一套状态图要给多个角色使用时，只能复制一遍组装代码。
- 测试想构造多个互相独立的实例，没有统一入口。
- 图结构无法作为数据被检查、比较、复用。
- 已有的 `PlayableStateMachineState<T>`（方案 D 的雏形）要求外部先把状态机建好再传进去，无法做到「每次进入重新构建一份子机」。

方案 A 把「描述」和「实例」拆开：

```text
Definition（图描述） --Build(context)--> Instance（可运行状态机）
```

一份 Definition 可以 Build 任意多次，每次得到完全独立的状态、转移和 Timeline。

## 2. 目标与非目标

### 目标

1. 状态图以 key 描述，支持一份定义生成多个实例。
2. 转移条件可以读取构建时传入的 `Context`，不再依赖闭包捕获。
3. 保留现有 `AddState` / `AddTransition` / `Transition.Triggers` API，旧代码零改动。
4. Inspector 继续消费 `IStateMachineInspection`，不需要感知 Blueprint。
5. Playable 层同样支持 Blueprint，且每次 Build 的 Timeline 完全独立。

### 非目标

1. 不做 ScriptableObject / JSON 序列化。Blueprint 先保持纯 C# 对象。
2. 不做可视化图编辑器。
3. 不在本阶段实现「子图作为状态」的 Definition 版本（方案 D 单独做）。
4. 不做热重载和运行时改图。

## 3. 总体结构

```text
StateMachineBlueprintBase<T, TMachine, TSelf>
├── StateMachineBlueprint<T>              -> StateMachine<T>
└── PlayableStateMachineBlueprint<T>      -> PlayableStateMachine<T>

Build(context)
  1. CreateMachine()
  2. machine.Context = context
  3. 遍历 stateFactories，逐个创建状态并 AddState(key, state)
  4. 遍历 transitionSpecs，按 key 解析源/目标，创建转移并注册
  5. 设置 Entry 初始状态
  6. 返回 machine
```

关键约束：

- `stateFactories` 里的委托**每次 Build 都会执行**。
- Blueprint 不缓存任何状态实例、转移实例或 Timeline。
- Build 完成后，Blueprint 与实例之间没有引用关系。

## 4. API 设计

### 4.1 条件接口

```csharp
public interface ITransitionCondition<T>
{
    bool Evaluate(T context);
}

public sealed class DelegateTransitionCondition<T> : ITransitionCondition<T>
{
    readonly Func<T, bool> predicate;

    public DelegateTransitionCondition(Func<T, bool> predicate)
    {
        this.predicate = predicate ?? throw new ArgumentNullException(nameof(predicate));
    }

    public bool Evaluate(T context) => predicate(context);
}
```

`Transition<T>` 增加条件列表与 context 求值：

```csharp
public IReadOnlyList<ITransitionCondition<T>> Conditions { get; }
public int TriggerCount { get; }          // 旧 triggers + 新 conditions
public bool HasTriggerConditions { get; }

public void AddCondition(ITransitionCondition<T> condition);
public bool RemoveCondition(ITransitionCondition<T> condition);

public bool Evaluate(T context);          // 新，状态机内部统一走这个
public bool IsTriggered { get; }          // 旧，等价于 Evaluate(default)
```

求值顺序：先旧 `Func<bool>` 列表，再 `ITransitionCondition<T>` 列表，全部为 AND，遇 false 短路。

`LastTriggerResult` / `HasTriggerResult` 仍然只作为**调试遥测**：每次调用都会重新求值，不存在跨帧缓存导致条件不更新的问题。

### 4.2 keyed 状态注册

`StateMachine<T>` 增加：

```csharp
public IReadOnlyDictionary<string, IState<T>> StatesByKey { get; }

public void AddState(string key, IState<T> state);
public IState<T> FindState(string key);       // 找不到返回 null
public IState<T> GetState(string key);        // 找不到抛 StateKeyNotFoundException
public void SetInitialState(string key);
public void ChangeStateTo(string key);
```

规则：

- key 非空且在同一台机器内唯一。
- 一个状态实例只能挂一个 key。
- `RemoveState` 会同时清理该状态的所有 key。
- 旧的无 key `AddState` 保持原行为，不与 keyed 表冲突。

### 4.3 Blueprint

```csharp
public abstract class StateMachineBlueprintBase<T, TMachine, TSelf>
    where TMachine : StateMachine<T>
    where TSelf : StateMachineBlueprintBase<T, TMachine, TSelf>
{
    public string Name { get; }
    public IReadOnlyDictionary<string, Func<IState<T>>> StateFactories { get; }
    public IReadOnlyList<TransitionSpec<T>> TransitionSpecs { get; }
    public string EntryKey { get; }

    public TSelf State(string key, Func<IState<T>> factory);
    public TSelf State<TState>(string key) where TState : IState<T>, new();
    public TSelf Transition(string from, string to,
        ITransitionCondition<T> condition = null, Action<T> onTriggered = null);
    public TSelf Transition(string from, string to,
        Func<T, bool> condition, Action<T> onTriggered = null);
    public TSelf Entry(string key);

    public TMachine Build(T context);

    protected abstract TMachine CreateMachine();
    protected virtual Transition<T> CreateTransition(
        TMachine machine, IState<T> source, IState<T> destination, TransitionSpec<T> spec);
}
```

具体类型：

```csharp
public class StateMachineBlueprint<T>
    : StateMachineBlueprintBase<T, StateMachine<T>, StateMachineBlueprint<T>>
{
    protected override StateMachine<T> CreateMachine() => new StateMachine<T>(Name);
}

public class PlayableStateMachineBlueprint<T>
    : StateMachineBlueprintBase<T, PlayableStateMachine<T>, PlayableStateMachineBlueprint<T>>
{
    public PlayableStateMachineBlueprint<T> PlayableTransition(
        string from, string to, float duration = 0f,
        ITransitionCondition<T> condition = null,
        Action<IPlayableState<T>, IPlayableState<T>, float> durationEvent = null,
        InterruptionMode interruptionMode = PlayableTransition<T>.INTERRUPTION_MODE_DEFAULT,
        Action<T> onTriggered = null);
}
```

`PlayableStateMachineBlueprint` 额外提供 `Func<T,bool>` 重载，便于写短 lambda。

### 4.4 TransitionSpec

```csharp
public sealed class TransitionSpec<T>
{
    public string SourceKey { get; }
    public string DestinationKey { get; }
    public ITransitionCondition<T> Condition { get; }
    public float Duration { get; }
    public InterruptionMode InterruptionMode { get; }
    public Action<IPlayableState<T>, IPlayableState<T>, float> DurationEvent { get; }
    public Action<T> OnTriggered { get; }
}
```

`Duration` / `DurationEvent` / `InterruptionMode` 只对 Playable Blueprint 有意义；core Blueprint 忽略它们。这样一份 spec 类型可以同时服务两层，避免两套几乎相同的描述结构。

### 4.5 用法示例

```csharp
public sealed class EnemyContext
{
    public float Distance;
    public bool Alerted;
}

var blueprint = new PlayableStateMachineBlueprint<EnemyContext>("Enemy")
    .State("idle", () => new IdleState())
    .State("chase", () => new ChaseState())
    .Entry("idle")
    .PlayableTransition("idle", "chase", 0.2f, ctx => ctx.Alerted)
    .PlayableTransition("chase", "idle", 0.25f, ctx => !ctx.Alerted);

var aggressive = blueprint.Build(new EnemyContext { Alerted = true });
var passive = blueprint.Build(new EnemyContext { Alerted = false });
```

两台机器共享同一份图描述，但状态实例、转移实例、Timeline 和 Context 全部独立。

## 5. Build 流程与校验

```csharp
public TMachine Build(T context)
{
    var machine = CreateMachine();
    machine.Context = context;

    foreach (var pair in stateFactories)
        machine.AddState(pair.Key, pair.Value());

    foreach (var spec in transitionSpecs)
    {
        var source = machine.GetState(spec.SourceKey);
        var destination = machine.GetState(spec.DestinationKey);
        var transition = CreateTransition(machine, source, destination, spec);
        transition.OnTriggered = spec.OnTriggered;
        if (spec.Condition != null)
            transition.AddCondition(spec.Condition);
        machine.AddTransition(transition);
    }

    if (!string.IsNullOrEmpty(entryKey))
        machine.SetInitialState(machine.GetState(entryKey));

    return machine;
}
```

校验点：

| 情况 | 行为 |
| --- | --- |
| key 为空 | `ArgumentException` |
| key 重复 | `DuplicateStateKeyException` |
| 同一状态挂第二个 key | `StateMachineException` |
| 转移引用了不存在的 key | `StateKeyNotFoundException` |
| Entry 引用了不存在的 key | `StateKeyNotFoundException` |
| Build 时 factory 返回 null | `StateMachineException` |

未设置 Entry 时沿用旧行为：首个注册状态作为初始状态。

## 6. Context 与条件

- `machine.Context = context` 在注册状态前设置；`AddState` 会把它注入每个状态。
- 条件通过 `Evaluate(context)` 读取同一个 Context 实例，适合写「距离小于 5」「血量低于 30%」这类依赖运行时数据的判断。
- 旧的无参 `IsTriggered` 等价于 `Evaluate(default)`。**依赖 Context 的条件不要走旧路径**，否则拿到的是 `default(T)`。
- 状态机内部所有求值点统一改为 `transition.Evaluate(context)`：
  - `StateMachine.Evaluate`
  - `PlayableStateMachine.TransitionState.CheckInterruption`

## 7. 实例隔离规则

这是方案 A 的核心，必须写进代码评审清单：

1. 状态工厂每次 Build 必须返回**新实例**。禁止 `() => sharedIdle`。
2. Playable 状态在构造时创建自己的 Timeline，因此更不能共享状态实例。
3. Blueprint 本身不持有 `IState<T>`，只持有 `Func<IState<T>>`。
4. Build 出来的机器之间不共享转移对象；`Transition<T>` 的 `LastTriggerResult` 是实例字段。
5. Blueprint 配置完成后视为只读；Build 不是线程安全的，不要并发调用，也不要在 Build 期间修改 Blueprint。

## 8. 兼容性

| 旧 API | 状态 |
| --- | --- |
| `AddState(IState<T>)` | 保留 |
| `SetInitialState(IState<T>)` | 保留 |
| `AddTransition(source, destination, Func<bool>)` | 保留 |
| `Transition.Triggers` | 保留 |
| `Transition.IsTriggered` | 保留，走 `default` context |
| `IStateMachineInspection` | 不变 |

Inspector 的「条件数」从 `Triggers.Count` 改为 `TriggerCount`（旧触发器 + 新条件），显示逻辑不变。

## 9. 迁移步骤

1. **核心层**：条件接口、`Transition` context 求值、keyed 状态、异常类型。
2. **Blueprint**：core + playable，两种工厂。
3. **示例迁移**：`StateMachineDebugExample` 改为 Blueprint 构建，验证 5 状态图行为不变。
4. **测试**：新增 `StateMachineBlueprint_Test`，覆盖实例隔离、context 条件、key 校验、Playable Timeline 独立性。
5. **后续**：项目内其他手写组装点逐个迁移；方案 D 的 `SubStateMachineDefinition<T>` 直接持有 Blueprint，进入时 `Build` 出独立子机。

## 10. 验收标准

- 同一 Blueprint Build 两次，状态实例引用不同。
- 两台机器的 Context 不同，同一条件只让其中一台转移。
- 重复 key、缺失 key 均抛出明确异常。
- Playable Blueprint 每次 Build 的转移 Timeline 是不同对象，过渡时长生效。
- 旧 `StateMachine_Test` / `StateMachineInspection_Test` 全部通过。
- `StateMachineDebugExample` 行为与迁移前一致。

## 11. 风险与后续

| 风险 | 处理 |
| --- | --- |
| key 拼写错误只能运行时发现 | 后续加 Editor 校验或 key 常量类 |
| 工厂里捕获了外部可变状态 | 评审规则：工厂只负责 new，不读外部状态 |
| Blueprint 被并发 Build | 文档标注非线程安全；需要时由调用方加锁 |
| 条件异常被包装成 `StateTransitionException` | 沿用现有异常包装，消息带源状态名 |
| 方案 D 接入时子机生命周期 | D 阶段单独处理，A 只保证 Build 出来的机器可独立运行 |
