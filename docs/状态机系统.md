# MNAC 分层状态机系统（`MNAC.States`）

> 项目：MNAC（迷你装甲核心）
> 位置：`Assets/Scripts/States/`，程序集 `MNAC.States`
> 本文档基于对现有源码的实际核对编写，用于介绍状态机系统架构与使用方式。
> 标注【现有】= 已实现的现有代码能力；【待完善】= 代码中 TODO / 被注释 / 未完成的部分。

---

## 1. 一句话介绍

`MNAC.States` 是一套**泛型分层状态机库**，围绕三个核心能力设计：

1. **状态机本体**：`StateMachineBase<S,T>` —— 注册状态、注册转移、每帧检测转移并切换状态。
2. **可播放状态（Playable）**：给每个状态挂一条 `Timeline`（进度条），让"状态切换"变成一个**有时间跨度的过渡动画**（Blend/播放），而不是瞬间切换。
3. **三种载体（三件套）**：同一套逻辑提供 纯 C# 类 / `MonoBehaviour` 组件 / `ScriptableObject` 配置 三种形态，分别对应"代码内搭状态机 / 挂到场景里用 / 配置资源驱动"。

依赖：`MNAC.Utilities`（`Timeline`、`Blackboards`、`Composable`）。整个库**只依赖 Timeline 做时间管理，不绑定 Animator**，动画状态机（`AnimationStateMachine<T>`）是单独的一层薄封装。

## 2. 整体架构

```
MNAC.Utilities（Timeline / Blackboard / Composable）
        ▲
MNAC.States
        ├─ 状态机：StateMachineBase<S,T>  →  StateMachine<T>  →  AnimationStateMachine<T>
        │           │
        │           └─ PlayableStateMachine<T>  →  WithCallbackPlayableStatemachine<T>
        │
        ├─ 状态：   IState<T>  →  StateBase<T>  →  PlayableStateBase<T>  →  WithCallbackPlayableState<T>
        │                                                            →  StateComponentNode<T>（Composable）
        │           StateBase<T>  →  AnimationStateBase<T>
        │
        ├─ 转移：   ITransition<T>  →  Transition（内嵌于 StateMachineBase）
        │                        └→  PlayableTransition<T>  →  BlendingTransition<T>  →  SubStatemachineTransition<T>
        │
        └─ 子状态机：SubStatemachineState<T> / WithCallbackStatemachineState<T> / PlayableStatemachineState<T>
```

### 2.1 核心继承链（均已核对）

**状态（State）**
- `IState<T>` → `StateBase<T>`（实现转移增删查、`OnEnter/OnUpdate/OnExit`）
- → `PlayableStateBase<T>`（+ `Timeline`、过渡回调虚方法）
- → `WithCallbackPlayableState<T>`（+ `EntryAction / UpdateAction / ExitAction` 三个委托，用委托驱动生命周期）
- → `StateComponentNode<T>`（`MNAC.Utilities.Composable` 命名空间，+ 黑板 + `IComponent` 节点，供可组合组件系统复用）

**状态机（StateMachine）**
- `StateMachineBase<S,T>`（泛型核心）→ `StateMachine<T>` → `AnimationStateMachine<T>`
- `StateMachineBase<S,T>` 另派生 `PlayableStateMachine<T>` → `WithCallbackPlayableStatemachine<T>`

**转移（Transition）**
- `ITransition<T>` / `IReadonlyTransition<T>`
- `StateMachineBase<T>.Transition`（内嵌嵌套类，核心实现）
- → `PlayableTransition<T>`（+ `Timeline`、`InterruptionSource`、过渡回调事件）
- → `BlendingTransition<T>`（+ `offset` / `fixedExitTime`，混合过渡）
- → `SubStatemachineTransition<T>`（进入子状态机并切换到其目标状态）

### 2.2 三种载体（三件套）

| 载体 | 命名 | 状态 | 状态机 |
|---|---|---|---|
| 纯 C# | — | `StateBase<T>` / `PlayableStateBase<T>` / `WithCallbackPlayableState<T>` | `StateMachine<T>` / `PlayableStateMachine<T>` |
| MonoBehaviour | `_MonoComponent` | `State_MonoComponent<T>` / `PlayableState_MonoComponent<T>` / `WithCallbackPlayableState_MonoComponent<T>` | — |
| ScriptableObject | `_SO` | `State_SO<T>` / `PlayableState_SO<T>` / `WithCallbackPlayableState_SO<T>` | — |

所有载体都持有**内部状态实例**（`_state`），`Awake`/`OnEnable` 时通过 `CreateInternalState()` 创建，把接口调用转发给内部状态。**注意**：内部默认状态的 `OnEnter/OnExit/OnUpdate` 是 `NotImplementedException`，使用时必须继承并实现生命周期方法（见 §6.4 的坑）。

## 3. 核心概念

### 3.1 状态 `IState<T>`
- `Name`：状态名（用于日志 / 调试）
- `ID`：`Guid`（每个实例唯一）
- `Enabled`：是否启用。**转移检测时目标状态必须 `Enabled` 才生效**（`StateMachineBase.CheckTransitions`）。
- `Context`：泛型上下文 `T`，在 `AddState` 时注入、机器统一分发，状态间共享数据。**状态机设置 `Context` 会把值广播给所有状态**。
- `Transitions`：本状态出边的转移表。
- 生命周期：`OnEnter()` / `OnUpdate()` / `OnExit()`。

### 3.2 转移 `ITransition<T>`
- `SourceState` / `DestinationState`：起点与终点。
- `TriggerEvents`：`IReadOnlyList<Func<bool>>`，**多个条件是与关系**（全部为 true 才触发）。可动态 `AddTriggerEvent` / `RemoveTriggerEvent` / `ClearTriggerEvents`。
- `TriggeredEvent`：触发成功时回调（携带 `Context`）。
- 空触发条件列表 = **无条件转移**（当前帧必然切换）。

### 3.3 Timeline（`MNAC.Utilities.Timeline`）
每个可播放状态/转移带一条时间线：
- `Duration`（长度）→ `NormalizedTime`（归一化进度 0~1）
- 事件：`StartAction` / `EndAction` 回调、`AddPointEvent(p, action)` 点事件、`AddRangeEvent(start, dur, action)` 区间事件
- `Restart()` / `Start()` / `Pause()` / `End()` / `OnUpdate(dt)`

## 4. 运行流程

`StateMachineBase.OnUpdate()` 每帧执行：
1. 无当前状态且已注册状态 → 进入第一个状态（`states.First()`）。
2. `CheckTransitions()`：遍历当前状态出边，若目标 `Enabled` 且（无条件 **或** 所有 `TriggerEvents` 为 true）→ 先 `TriggeredEvent.Invoke(context)`，返回该转移。
3. 有转移 → `ChangeState(transition)`：先 `当前状态.OnExit()`，再 `目标状态.OnEnter()`，更新 `currentState`。
4. `currentState.OnUpdate()` 更新当前状态。

`PlayableStateMachine` 在其上扩展：切换时把**转移本身做成一个临时状态**（`TransitionState`），用转移的 `Timeline` 播放过渡，`NormalizedTime >= 1` 时才真正进入目标状态。因此可播放状态机的切换是"先过渡、后到达"。

### 4.1 可播放状态机的一次切换（时序）

```
当前状态A --(转移触发)--> TransitionState（播放转移的Timeline）
   │                        │
   │   transition.StartAction → sourceState.ToNextStateTransitionBegin
   │   0~1 RangeEvent        → sourceState.ToNextStateTransitionRunning
   │   transition.EndAction  → sourceState.ToNextStateTransitionEnd
   │                          │ destinationState.FromPreviousStateTransitionBegin/Running/End
   │                          │（Timeline播完，NormalizedTime>=1）
   ▼                          ▼
                          目标状态B.OnEnter
```

### 4.2 中断（InterruptionSource）
`PlayableTransition` 带 `InterruptionSource`（`None` / `Next`，默认 `Next`）。为 `Next` 时，过渡播放期间会把**目标状态的出边**临时挂到过渡状态上，允许在过渡中途被下一次切换打断。

## 5. 状态机的三大家族

### 5.1 普通状态机 `StateMachine<T>`（`StateMachineBase<StateBase<T>, T>`）
最基础。适合逻辑不依赖时间线、状态即查即切的场景。用法：
```csharp
var sm = new StateMachine<MyContext>("logic", enabled: true);
sm.AddState(new IdleState());
sm.AddState(new RunState());
sm.AddTransitionFor(idle, run, () => input.Speed > 0);   // 条件转移
sm.AddTransitionFor(run, idle, () => input.Speed <= 0);
sm.OnUpdate();  // 每帧驱动
```

### 5.2 可播放状态机 `PlayableStateMachine<T>`（`StateMachineBase<IPlayableState<T>, T>`）
- `AddTransitionFor(state, dest, triggerEvent)`：默认 0 时长、默认中断源的快捷方式。
- `AddTransitionFor(state, dest, duration, triggerEvent, durationEvent, interruptionSource)`：完整版，`durationEvent` 是过渡期间逐帧回调 `(src, des, normalizedTime)`，可用来驱动权重混合。
- 状态也可设置 `ExitWhenEnd`（`[Obsolete]`）：标记后需等状态 Timeline 播完才能转移（`CheckTransitions` 里做了 `NormalizedTime >= 1` 校验）。

### 5.3 带回调状态机 `WithCallbackPlayableStatemachine<T>`
在 `PlayableStateMachine` 基础上支持 `EntryAction` / `UpdateAction` / `ExitAction` 三个委托，供外部把逻辑挂进生命周期，不需要子类化。

## 6. 状态类详解

### 6.1 `StateBase<T>`（所有状态的基座）
- 数组实现转移表（`ITransition<T>[]`，通过 `Array.Resize` 增删）。
- `FindTransition(destination)`：按目标状态查找。
- `AddTransition` 会去重（同目标只留一条）。

### 6.2 `PlayableStateBase<T>`
- 构造带 `duration`，默认创建 `Timeline(duration)`（可重写 `NewTimeline`，比如 `TransitionState` 返回 null）。
- 提供六个过渡回调虚方法（`FromPreviousStateTransitionBegin/Running/End`、`ToNextStateTransitionBegin/Running/End`），让状态感知"我从哪个状态过渡而来 / 正在过渡去哪个状态"。

### 6.3 `WithCallbackPlayableState<T>`
生命周期改为委托驱动：
```csharp
state.EntryAction += () => Debug.Log("进入");
state.UpdateAction += dt => ...;
state.ExitAction += () => Debug.Log("离开");
```

### 6.4 `AnimationStateBase<T>` / `AnimationStateMachine<T>`
薄封装：状态持 `Animator` 引用，暴露 `OnAnimationIK(layerIndex)` 钩子，机器转发 `OnAnimatorIK` 给当前状态。仅此一层，动画播放仍需自行用 Animator / Playables 完成。

## 7. 过渡（Transition）详解

### 7.1 `PlayableTransition<T>`
构造参数：`(sourceState, destinationState, triggerEvent, durationEvent, duration, interruptionSource)`。内部为过渡创建 Timeline，并把以下事件挂上去：
- 开始 → `sourceState.ToNextStateTransitionBegin(this)` 与 `destinationState.FromPreviousStateTransitionBegin(this)`
- 全程 → `ToNextStateTransitionRunning` / `FromPreviousStateTransitionRunning`
- 结束 → `ToNextStateTransitionEnd` / `FromPreviousStateTransitionEnd`

### 7.2 `BlendingTransition<T>`（混合过渡，最常用）
在 `PlayableTransition` 基础上增加两个参数，用于"目标动画从中间开始播，而不是从头开始"：
- `offset`：目标 Timeline 前进的偏移量（`newLength = oldLength - (offset + duration)`，即把目标状态开头 `offset` 段时间"吃掉"）。
- `fixedExitTime`：源状态播到该归一化时刻时强制触发转移（非 `-1` 时自动添加一个触发条件）。
- 切换时通过 `Begin` 缩短目标 Timeline，退出时 `ResetDestinationState` 恢复原长度。

**用途示例**：跑动 → 跳跃，希望跳跃动画从"起跳中段"开始接，用 `offset`；攻击动画想在第 3 帧出伤就切，用 `fixedExitTime`。

### 7.3 `SubStatemachineTransition<T>`
进入子状态机，并在过渡开始时立即把子状态机切到指定目标状态（`AddPointEvent(0, ...)`）。

---

## 8. 子状态机（分层）

三种把"状态机当状态用"的形态：

| 类型 | 行为 |
|---|---|
| `SubStatemachineState<T>` | 包装一个 `WithCallbackPlayableStatemachine<T>`，进入时 `ChangeStateTo(targetState)` 并把子机的过渡回调向上透传；Timeline 复用目标状态长度 |
| `WithCallbackStatemachineState<T>` | 包装子机，生命周期与过渡回调全部转发 |
| `PlayableStatemachineState<T>` | 包装 `PlayableStateMachine<T>`，同上 |

用途：把"待机→奔跑→跳跃"等整组状态封装成一个大状态（如"地面运动"），再在外层状态机里与"飞行/死亡/驾驶"并列。

---

## 9. 与项目其他系统衔接

- **Composable**：`StateComponentNode<T>`（`MNAC.Utilities.Composable`）把状态机节点接到可组合组件树（`IComponent`/`ComponentNode`/黑板）上，用于"行为由配置组装"。
- **Blackboard**：状态间共享数据走 `Context`，全局数据走黑板。
- **Animator**：`AnimationStateMachine<T>` 仅在需要 IK 回调时使用。

**装配转移**（`PlayerTargetLocker.cs:268-295`）：
```csharp
void InitializeStatemachine(float receiveInputDuration)
{
    _lockedState  = new(this, "locked");
    _receiveState = new(this, "receive_input", receiveInputDuration);
    _findClosestTargetState_OP = new(this, "find_target_op");
    _findClosestTargetState_MT = new(this, "find_target_mt");

    statemachine = new();
    statemachine.AddState(_findClosestTargetState_OP);
    statemachine.AddState(_lockedState);
    statemachine.AddState(_receiveState);
    statemachine.AddState(_findClosestTargetState_MT);

    statemachine.AddTransitionFor(_findClosestTargetState_OP, _lockedState, () => _mainLockTarget != null);
    statemachine.AddTransitionFor(_lockedState, _receiveState, () => _cursorPositionDelta != Vector3.zero);
    statemachine.AddTransitionFor(_lockedState, _findClosestTargetState_OP, () => _mainLockTarget == null);
    statemachine.AddTransitionFor(_receiveState, _lockedState,
        () => _cursorPositionDelta == Vector3.zero && _receiveState.Timeline.NormalizedTime < 1);
    statemachine.AddTransitionFor(_receiveState, _findClosestTargetState_MT,
        () => _receiveState.Timeline.NormalizedTime >= 1);
    statemachine.AddTransitionFor(_findClosestTargetState_MT, _lockedState, () => _mainLockTarget != null);
    statemachine.AddTransitionFor(_findClosestTargetState_MT, _findClosestTargetState_OP, () => _mainLockTarget == null);
}
```
驱动：在 `OnFixedUpdate()` 里调 `statemachine.OnUpdate()`。

> 要点：状态用 `duration` 构造 → 自带 `Timeline`，转移条件里可直接读 `state.Timeline.NormalizedTime` 做"播完才走"的逻辑，无需额外计时。

### 10.3 示例 C：裸 `StateBase` 手动切换（不用状态机容器）

`Assets/Scripts/Behaviours/Arms/Animation/ArmAnimationCore.cs` 里的 `ArmAnimationPlayingState` / `SwitchingState` 是纯 `StateBase` 子类，不用机器，手动走生命周期：
```csharp
void UpdatePlayingState(byte statusNum)
{
    _playingState?.OnExit();
    var newState = GetNewState(statusNum);
    newState.OnEnter();
    _playingState = newState;
}
```
说明：`StateBase` 本身是自洽的状态，机器只是"每帧检测转移 + 调生命周期"的容器，可以拆开单独用。

### 10.4 项目实际用法统计（调研结论）

1. 顶层机器**全部用 `WithCallbackPlayableStatemachine<object>`**；裸 `StateMachine<T>` / `PlayableStateMachine<T>` 只作为子状态机/字段类型出现（如 `ArmController`、`NormalState`）。
2. 状态**几乎全是 `WithCallbackPlayableState` 系**；唯一裸用 `StateBase` 的是 `ArmAnimationCore` 的手动切换场景。
3. 分层 = 把子状态机实例当状态 `AddState` 进去 + `SubStatemachineTransition` 指定进入子状态。
4. 状态上下文 `Context` 多用 `<object>`，实际共享数据靠状态持有外部引用（如 `PlayerTargetLocker<T>` 的 `T` / `LocomotionStateContext`）。

## 11. 已知问题与坑（实测）

1. **`State_MonoComponent`/`State_SO` 内部默认状态会抛 `NotImplementedException`**：继承时若没实现 `OnEnter/OnExit/OnUpdate`，运行时必炸。
2. **`WithCallbackPlayableState_MonoComponent` / `_SO` 的 `CreateInternalState` 创建的内部状态会抛 `NotImplementedException`**：这些组件/配置形态目前**没有实现内部状态的生命周期**，仅回调委托可用（见 §12 评价）。
3. **`StateBase<T>.transitions` 与 `PlayableStateBase<T>._transitions` 双份缓存**：`PlayableStateBase.AddTransition` 同时维护两份，新增转移必须走该方法，直接改内部数组会不同步。
4. **`Context` 广播用 `foreach` 遍历 `states`，含当前状态机器上所有状态**：大状态机下每帧 `Context` 赋值是 O(n)。
5. **`CheckTransitions` 里目标状态需 `Enabled`**：想"禁用某状态使转移失效"可以直接用这个机制，但注意行为较隐蔽。
6. **`TransitionState` 的 Timeline 若为 null（`NewTimeline` 返回 null 的场合）会抛 `NullReferenceException`，被捕获后降级为直切目标状态**：`PlayableStateMachine.ChangeState` 里以 `Debug.Log` 提示，属规避性代码。
7. **大量 `[Obsolete]` / 被注释代码**：`ExitWhenEnd`、`AddTransition(ITransition)`、`State_MonoComponent.OnEnable/OnDisable`、`StateMachineBase.ChangeState` 里被注释的 `StateExitException`/`StateEntryException` 包装等，说明系统迭代中未清理。
8. **命名空间 `Tests.States` 为 `rootNamespace`，但实际类都在 `MNAC.States`**：asmdef 的 `rootNamespace` 与真实命名空间不一致，新文件别被 IDE 自动生成的 namespace 带偏。

## 12. 代码质量评价

> 以下为对 `MNAC.States` 现状的客观评价，不吹不黑，按"优点 / 问题 / 总体结论"组织。

### 12.1 优点

1. **抽象层次清晰，扩展点留得好**。`StateMachineBase<S,T>` → `PlayableStateMachine<T>` → `WithCallbackPlayableStatemachine<T>` 的分层，让"普通机器 / 带过渡的机器 / 带回调的机器"三个能力级别各自独立，使用者按需选择（项目里实际只用到了最顶层）。
2. **"转移即临时状态"的设计很有想法**。把过渡本身做成一个 `TransitionState` 并播放转移 Timeline，天然支持过渡中断（`InterruptionSource.Next`）、过渡期间可被再切换、以及六个 `From/To…TransitionBegin/Running/End` 回调，信息很全——这在纯回调式的状态机里通常要手写不少样板。
3. **Timeline 抽象独立、可复用**。`Timeline` 带点事件 / 区间事件 / 归一化进度，不仅状态机用，`BlendingTransition`、`SubStatemachineTransition`、项目里其他计时场景（如 `PlayerTargetLocker` 的 `receive_input`）都在复用，是个合格的基础设施。
4. **三件套（类 / Mono / SO）形态齐全**，`Composable` 能接到黑板和组件树上，方向正确（组件化装配的愿景）。
5. **真·泛型**：全部类型带 `<T>`，连非泛型版本都是 `: xxx<object>` 的薄壳，没有为了省事砍泛型。

### 12.2 问题

1. **骨架状态 / 半成品偏多**（与 CLAUDE.md 记录的"功能多为早期骨架"一致）：
   - `State_MonoComponent`/`State_SO` 内部默认状态**只抛异常不实现**；`WithCallbackPlayableState_MonoComponent`/`_SO` 的内部状态同样没实现生命周期。**这意味着 Mono / SO 两个载体在生命周期上是"假实现"**，只有回调委托可用。
   - 大量 `[Obsolete]`（`ExitWhenEnd`、`AddTransition(ITransition)`）、被注释代码（`ChangeState` 里被注释的 `StateExitException`/`StateEntryException` 包装、`Timeline.cs` 里整段注释掉的 `_V1/_V2`）、`TODO：删除无用代码`。**"迭代了两版、新旧并存"的痕迹明显**。
2. **异常处理名存实亡**。定义了 4 个异常类（`StateNotExistException`/`StateEntryException`/`StateExitException`/`StateUpdateException`），但 `ChangeState` 里捕获后**原样 `throw`**（包装代码被注释掉），等于白写了异常体系，还没有运行时错误兜底（第一行就写着 `TODO：完善状态运行时的错误捕获`）。
3. **效率与 GC**：
   - `CheckTransitions` 每帧对所有出边做**全量 `Func<bool>` 求值**，且每次切换 `ChangeState` 里 `OnExit/OnEnter` 无缓存。
   - `StateBase` 转移表用 `Array.Resize` + `Array.FindIndex`，小规模没问题，但状态一多、每帧检测就是 O(边数)。
   - 转移的触发条件 `triggerEvents` 是 `List<Func<bool>>`，`Triggered` 属性每次全遍历——高频状态机上这是每帧必付的代价。
4. **接口设计的自洽性瑕疵**：
   - `IState<T>.RemoveTransition(IState<T> destinationState)` 是**按目标状态删**而不是按转移对象删，语义略怪（同名目标只能一条，配合 `AddTransition` 的去重行为）。
   - `PlayableStateBase` 维护 `base.transitions` 与 `_transitions` 双份缓存，`AddTransition` 必须走特定路径，容易踩不同步的坑。
   - `IReadonlyTransition.Triggered` 是**状态相关属性**（每次求值），放进只读接口会让只读语义被破坏（读它会有副作用）。
   - 非泛型基类 `StateBase : StateBase<object>`、`StateMachine : StateMachine<object>` 的存在，加上 `Context` 默认 `<object>`，容易让新手以为泛型参数无关紧要。
5. **依赖面偏脏**：`StateMachineBase.cs` 顶部 `using Unity.VisualScripting`、`using Unity.VisualScripting.Antlr3.Runtime.Misc`，但代码里根本没用到——依赖污染且不满足"注释稀少但干净"的自我定位。
6. **文档与命名空间混乱**：asmdef `rootNamespace` 写 `Tests.States` 而真实命名空间是 `MNAC.States`；文件 `ArmedWeaponArmBehaviourBase.cs` 声明 `ArmedArmBehaviourBase` 之类的历史包袱在 States 里也存在（如 `PlayableStatemachineState` 拼写大小写不统一）。

### 12.3 总体结论

- **设计骨架值得肯定**：分层泛型状态机 + Timeline 化过渡 + 三件套载体的思路是清晰的，在动作游戏里"用时间线做状态过渡混合"是正确方向，`BlendingTransition`/`SubStatemachineTransition` 能实际跑起来并支撑起角色运动/锁定/生死这些核心逻辑，说明核心是**能用且被用起来**的。
- **完成度是主要短板**：新加入的 Mono/SO 载体是"样子货"（生命周期未实现），异常体系空转，旧代码未清理。**结论：适合作为项目自有状态机基础设施继续演进，但现阶段要引为公共框架使用，得先把 §12.2 的问题 1/2 收口**（实现 Mono/SO 生命周期、启用或删掉异常包装、清理 Obsolete）。
- 改进优先级建议：① 实现或删除 Mono/SO 的假生命周期；② 启用/移除异常包装，至少补运行时兜底日志；③ 清理 `Unity.VisualScripting` 无用 using 与 Obsolete 成员；④ 给 `StateBase` 转移表换 `List<ITransition<T>>` 或在状态内缓存转移索引。
